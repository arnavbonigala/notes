As we delve into&nbsp;&nbsp; databases, it's important to understand that&nbsp; database management systems (DBMS) are crucial,&nbsp;&nbsp; heavily used, and fascinating pieces of&nbsp; software. They are responsible for recording&nbsp;&nbsp; and retrieving data, serving as the primary&nbsp; data storage for most software applications. A DBMS organizes information into&nbsp; tables, which are collections of records,&nbsp;&nbsp; or rows. Each row has a value&nbsp; for every column in the table.&nbsp;&nbsp; For example, you could have a table&nbsp; with three records—one for Berkeley,&nbsp;&nbsp; one for Cambridge, and one for Minneapolis—and&nbsp; three columns: latitude, longitude, and name. A column has a name and also a type. So, in our&nbsp; example, the "name" column would be strings,&nbsp;&nbsp; while "latitude" and "longitude" would&nbsp; be numbers. If you look across a row,&nbsp;&nbsp; you'll see values of different types. A row is&nbsp; simply a value for each column in the table. The Structured Query Language, often called SQL,&nbsp;&nbsp; is perhaps the most widely used programming&nbsp; language in the world. It's the language you&nbsp;&nbsp; use to interact with a database. SQL is&nbsp; also a declarative programming language,&nbsp;&nbsp; which gives it different properties&nbsp; from the languages we've studied so far. In brief, declarative languages have programs&nbsp; that describe the desired result of a computation,&nbsp;&nbsp; instead of describing how to compute it. You&nbsp; simply describe what you want to compute,&nbsp;&nbsp; and it's up to the interpreter to figure out&nbsp; how to efficiently and effectively generate&nbsp;&nbsp; the result for you. So, instead of spending a&nbsp; lot of time thinking about the process that's&nbsp;&nbsp; going to build the resulting data you&nbsp; want, you just state what data you want,&nbsp;&nbsp; and it's up to the computer to figure&nbsp; out how to compute or build it for you. Imperative languages like Python and&nbsp; Scheme are different. Their programs&nbsp;&nbsp; are descriptions of computational processes,&nbsp; and the interpreter carries out the execution&nbsp;&nbsp; or evaluation rules for the processes&nbsp; we describe. So, with SQL, we move from&nbsp;&nbsp; describing the process of computing a&nbsp; result to just describing the result. The role of a query is to take an&nbsp; existing table, like our cities table,&nbsp;&nbsp; and build another table. In this case, we'll&nbsp; create one that has "West Coast" as one of the&nbsp;&nbsp; values in each row, along with the name of&nbsp; the city. It won't include all the cities,&nbsp;&nbsp; only the ones where the longitude is large&nbsp; (meaning they are on the West Coast),&nbsp;&nbsp; and it will order these cities by&nbsp; their latitude from least to greatest. That would produce a table that looks like this: Region, Name&nbsp; West Coast, Los Angeles West Coast, Berkeley This new table has a "Region" column (because&nbsp; we asked for it) and a "Name" column (because&nbsp;&nbsp; we included the name). Most importantly, the rows it&nbsp;&nbsp; selected are not all the rows in the cities table,&nbsp; but only the ones that have a large longitude. Just with this one example, you get a flavor&nbsp; for how SQL works. You don't have to specify&nbsp;&nbsp; whether you want to sort by longitude and pick the&nbsp; first few, or iterate over the rows and append the&nbsp;&nbsp; rows with a high longitude to some list. You just&nbsp; say you want rows with a high longitude, and it's&nbsp;&nbsp; up to the system to figure out whether to do that&nbsp; before it orders by latitude or afterwards, before&nbsp;&nbsp; it selects out the name or afterwards. All those&nbsp; details really aren't your problem. Your problem&nbsp;&nbsp; is just to describe the table you want to build,&nbsp; and SQL will find a way to build it for you.
